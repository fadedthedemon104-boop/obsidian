Cloud-Sync Design (suggested)

Prefer a small backend to avoid exposing Personal Access Tokens in client code. Below are suggested endpoints and behaviors.

Recommended API endpoints (REST)

GET  /api/v1/backups/:userId?path=backups/habits.json
  - Returns: 200 { version, created_at, data } OR 404

PUT  /api/v1/backups/:userId?path=backups/habits.json
  - Body: { version, created_at, data }
  - If file exists: use If-Match / ETag for concurrency or provide lastSha in body.
  - Returns: 200 { ok, commitSha } or 201 created

POST /api/v1/backups/:userId/merge
  - Body: { client: { version, data }, mode: "merge|force" }
  - Server merges with remote using union-by-date or custom strategy; returns merged object and commit info.

Auth & Security

  • Use OAuth (GitHub app) or server-side Personal Access Token stored securely — never store PATs in client web apps.
  • Authenticate users with JWT/session; backend performs GitHub API calls on behalf of user.
  • Use ETags or commit SHA to detect concurrent updates and prevent accidental overwrites.

Conflict resolution strategy

  1. Default: Merge by date key — union of habit IDs per date (idempotent & simple).
  2. If both sides modified the same date and the union produces >X items or unexpected values, present a human-readable diff and require manual resolution.
  3. Keep a server-side history (commits) to allow rollback.

Local file format & migration

{
  "version": "habit_tracker_v1",
  "created_at": "2026-08-14T12:00:00Z",
  "data": {
    "2026-08-14": [0,2,4],
    "2026-08-13": [0,1,2,4]
  }
}

Future versions can bump "version" and include migration notes. The server can store multiple versions or auto-migrate on PUT.
